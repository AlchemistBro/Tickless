## Phase 2 — Matching engine as a library

Market orders = IOC/FOK with protective price bound; STP cancels the taker (newest); cancel-all is expanded by `orders` into single cancels. Snapshot = canonical binary + sha256, includes caller's Kafka offset. ## Phase 5 — Deposits
**Plan:**
1. Chains in compose: `bitcoind` regtest and `anvil` (Foundry) with a test ERC-20 "USDT" (6 decimals) deployed deterministically by a one-shot `chain-init` job (contract source and the committed bytecode live in `contracts/`). The Anvil dev key is the public well-known one, used for the devnet faucet/deployer only (ADR).
2. `services/wallet`: derives deposit addresses from an **xpub only** (BIP32 non-hardened `m/44'/coin'/0'/0/i`; BTC p2wpkh `bcrt1…`, ETH EIP-55). One index per (user, chain), allocated in the wallet DB; registers the address with chainwatcher over gRPC before returning it. No private key in the service (ADR 0009 deposit address derivation).
3. `services/chainwatcher`: a chain-agnostic scanner over a small `Chain` interface (tip, block by height with its deposits), implemented for bitcoind JSON-RPC (`getblock` verbosity 2) and go-ethereum (native ETH + ERC-20 `Transfer` logs). Every processed block's hash and parent hash are stored; on a parent mismatch the scanner walks back to the common ancestor, marks the affected deposits `REORGED` and rescans. A block and its deposits commit in ONE transaction (restart mid-block = nothing half done). Deposit identity `(chain, txid, index)` is UNIQUE. Credit only at the confirmation threshold (BTC 2, ETH 12), emitted as `DepositConfirmed` through the outbox on `deposits.events`. ADR 0010 (reorg handling).
4. Ledger consumes `deposits.events` and credits against EXTERNAL with business key `deposit:{chain}:{txid}:{index}` (idempotent, same transaction as the effect). Gateway: `GET /v1/deposit-address?chain=`, `GET /v1/deposits` (status + confirmations); OpenAPI and the web terminal get a deposit widget.
5. Tests: scanner vs a fake chain (random reorgs, crash/restart mid-block, duplicate delivery), bitcoind regtest testcontainer with a real forced 3-block reorg (`invalidateblock` + alternative chain), Anvil integration for ETH/ERC-20, ledger duplicate-event test, e2e deposit → credit → trade, and the credit-latency measurement (target ≤ 10 s after the threshold).

## Phase 6 — Withdrawals and notifications
**Plan:**
1. `services/withdrawals` (own DB): state machine REQUESTED -> SCREENING -> (PENDING_REVIEW | APPROVED) -> SIGNING -> BROADCAST -> CONFIRMED | FAILED | REJECTED. Transitions are single SQL statements guarded by the expected from-state (no lost updates); every transition is an outbox event on `withdrawals.events`. Balance is held in the ledger at request time (hold `withdrawal:{id}`), released on REJECTED/FAILED, settled to EXTERNAL on BROADCAST. Address format validated per chain (bech32 for BTC regtest, EIP-55 or lower-case hex for ETH).
2. Limits: per-user daily cap (sum of non-failed withdrawals of the UTC day) in the withdrawals DB; above `REVIEW_THRESHOLD` the request goes to `PENDING_REVIEW` and a RabbitMQ review task is published; execution waits for an admin approval (role `admin` in JWT, separate endpoint).
3. Screening: asynchronous consumer of a RabbitMQ `screening` queue checks the destination against a local denylist file (deliberate simplification: no external AML provider, stated in code, ADR 0011).
4. 2FA: TOTP (RFC 6238) secret per user in identity (encrypted at rest with the existing `seal` package); the gateway requires a valid `X-TOTP` code on `POST /v1/withdrawals`. Verified by identity over gRPC.
5. Signer: separate binary `services/signer` with its own key (regtest key generated at first start, kept only in its volume); accepts sign requests over mTLS gRPC only from `withdrawals` (client certificate CN check). Withdrawals never see the key. Broadcast from the signer's hot wallet on bitcoind (sendrawtransaction) and Anvil (eth_sendRawTransaction).
6. Confirmation tracking reuses the chainwatcher scanner for the hot-wallet addresses (watch outgoing txids; CONFIRMED after the same threshold).
7. notifier: consumes RabbitMQ `notifications` (retry with exponential backoff and a dead-letter queue `notifications.dlq`), renders templates, sends via SMTP to Mailpit. Events: signup verification, deposit credited, withdrawal requested/sent, order filled (opt-in).
8. Tests: state machine table tests and random interleavings; limits edge cases at the UTC day boundary; mTLS rejects a foreign client; e2e withdrawal on BTC and ETH with a below-threshold (auto) and an above-threshold (admin-approved) case; chaos `SMTP fails` (Mailpit paused) asserts notifications are retried and land in DLQ after the retry budget, and that withdrawal state is unaffected; invariants 1-3 still hold after every e2e run.
Status: planning complete; implementation in slices, each committed with its tests.
